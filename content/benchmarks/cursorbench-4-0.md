## 评估对象

**能力：** 完成开发者日常会交给 Agent 的编码工作的能力，特点是需求写得短而含糊、改动跨多个文件。题目类型随版本增加：3.0 版（2026-03-11）是编辑、重构和修 bug；3.1 版（2026-05-19）加入代码库理解、找 bug、规划和代码审查；3.2 版（2026-07-08）加入指令遵循和高级工具使用；4.0 版（2026-09-10）加入长程任务，涉及编辑、重构、调查、意图理解、管理作业和遵守设计。榜单按「模型加推理强度」逐行排名；博客把它定位为比较 Cursor 产品里各模型质量的离线评测，没有单独说明用什么 Harness。

**指标：** 榜单只有一个 Score（百分数），博客称其为解决方案的正确性得分，具体算法没有公开。榜单同时列出每题平均成本、token 数和步数。官方说内部还评代码质量、效率和交互行为，这些不在公开榜单里。截至 2026-11-18 访问官方榜单页（更新日志最后一条是 2026-10-07），CursorBench 4.0 共 91 行成绩，最高是 60.4%（Gemini 4 Carbon，推理强度 High），其次是 60.1%（Gemini 4 Carbon，Medium）和 60.0%（Fable 5.2，Max）。官方注明分数有波动，小差距未必有统计意义，不同版本之间的分数不能直接比较。

## 任务格式

官方披露的任务形态是：Agent 拿到一个代码库和一段很短的任务描述，要在其中完成改动或给出调查结论。题目用 Cursor Blame 这个功能收集，它能从已提交的代码追溯到当初产生这段代码的那次 Agent 请求，于是得到「开发者的原始请求」和「最终提交的代码」这样一对，后者当作参考答案。很多题来自 Cursor 内部代码库和受控来源，目的是降低模型在训练数据里见过题目的风险。题目每隔几个月更新一批。时限、可用工具和步数上限没有披露。

**示例（题目未公开，以下为官方披露的任务形态）**

- **需求**（概括自介绍博客）：官方没有给出任何一道具体题目。只说明任务描述是有意保持简短的，不像公开 benchmark 那样用详细的 GitHub issue。
- **原始题目：** 未公开。榜单页和两篇博客（2026-11-18 访问）都没有贴出任何一道题的任务描述、代码库或评分标准；介绍博客的说法是题目多取自内部代码库和受控来源，以降低被模型在训练中见过的风险。
- **任务规模：** 博客称 CursorBench-3 的题目在改动行数上明显多于 SWE-bench Verified、Pro 和 Multilingual，并且从最初版本到 CursorBench-3，题目涉及的代码行数和文件数大约翻了一倍。
- **涉及的场景：** 官方举出的有多工作区的 monorepo 环境、调查生产日志、执行耗时较长的实验。
- **判分：** 因为需求含糊、正确做法不止一种，官方不用固定的测试断言，而用评分 Agent 来打分。

**数据格式：** 未公开。官方披露到的程度只有上面这些：每题由一段简短请求和一份来自真实提交的参考解组成，文件结构、字段和评分标准的写法都没有公布。

## 评估流程

1. **启动：** 外部无法运行。评测由 Cursor 内部执行，结果发布在官方榜单页；官方没有提供提交入口或申请评测的说明。
2. **环境与执行：** 没有披露运行环境。博客提到 CursorBench-3 的题目都能在一次会话内完成，并说因为题目来自非公开代码库，可以让 Agent 像真实工作时那样使用工具，不必像基于公开仓库的评测那样限制联网和 git 历史。
3. **判分：** 由评分 Agent 判断解决方案是否正确。评分 Agent 用什么模型、看哪些材料、按什么标准，官方没有说明。
4. **算分：** 榜单给出每个「模型加推理强度」组合的 Score 和每题平均成本，成本按各模型公开的 token 单价折算。Score 如何由单题结果汇总、每题跑几次，没有披露。
5. **配套的线上评测：** 官方说明 CursorBench 只是离线部分，另外用真实流量上的对照实验来发现离线评分看不出的退步；线上结果不计入榜单分数。
